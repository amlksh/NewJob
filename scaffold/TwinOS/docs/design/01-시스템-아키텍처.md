# DTOS 시스템 아키텍처 설계서

> 계획서 4장(전체 시스템 아키텍처)·9장(데이터·지식 저장 구조)의 구현 가능 보완판.

---

## 1. 설계 원칙

1. **Agent = 표준 계약을 구현하는 서비스**: 모든 Agent는 동일한 Task API 계약(03 문서)을 구현한다. Orchestrator는 Agent의 내부를 모른 채 계약만으로 호출한다. → Physical AI 확장 시 "새 Agent 추가"로 끝난다.
2. **참조 전달(pass-by-reference)**: Agent 간에는 대용량 파일(ODB, INP, FMU 결과)을 직접 주고받지 않는다. 모든 산출물은 Artifact Store에 저장하고 URI + 메타데이터만 전달한다.
3. **도구는 도구가 있는 곳에서 실행**: Abaqus/Dymola는 라이선스·OS 제약이 있으므로, 해석 서버에 상주하는 Runner 데몬이 큐에서 작업을 가져가 실행한다. 백엔드가 해석 서버로 들어가지 않는다(방화벽 친화적 pull 모델).
4. **모든 실행은 원장에 기록**: run-level ledger가 KPI 집계·감사 추적·품질 개선의 단일 소스가 된다.
5. **템플릿 우선, 자유 생성은 게이트 뒤에**: LLM 산출물 중 실행계(스크립트/INP)에 들어가는 것은 반드시 Quality Gate(룰 기반) → 필요 시 HITL 승인을 거친다.

계획서 4장의 6계층 구조를 유지하되, 다음을 추가/구체화했다.

| 계획서 | 보완 내용 |
|---|---|
| Orchestration Layer | Workflow Engine을 "LangGraph(제어) + Celery(실행)"로 분리. 제어 흐름과 장시간 작업 실행을 섞지 않는다 |
| Tool Layer | **Runner 데몬(pull 모델)** 로 구체화 — 라이선스/OS 제약 해결 |
| Knowledge Layer | Knowledge Graph는 Phase 3로 미루고, MVP는 Postgres 관계 테이블 + pgvector로 시작 |
| Evaluation Layer | KPI 집계가 가능하도록 run-level ledger 스키마를 명시 (아래 6장) |
| (신규) LLM Gateway | 모든 LLM 호출 단일 통로: 마스킹, 비용 계측, 모델 교체(온프레미스 전환 대비) |

## 3. 배포 토폴로지 (물리 뷰)

```
[사내망]
  ┌─ DTOS App Server (Linux, Docker Compose → 후에 k8s)
  │    api-gateway · orchestrator · report-agent · vnv-agent · mbse-agent
  │    postgres · redis · minio
  │
  ├─ 해석 서버 #1 (Abaqus 설치, Windows/Linux)
  │    abaqus-runner (데몬: Redis 큐 폴링 → abaqus job 실행 → 결과 MinIO 업로드)
  │
  ├─ 해석 서버 #2 (FMU/Python 환경)
  │    fmu-runner (FMPy 기반)
  │
  └─ (Phase 4) GPU 워크스테이션: Isaac Sim Runner

[외부]
  LLM API (Claude/OpenAI) ←─ LLM Gateway 경유(마스킹 후 호출)
```

- **MVP는 Docker Compose 단일 호스트 + 해석 서버 1대**로 충분하다. k8s 전환은 Phase 3(멀티 프로젝트 동시 운영 시점)에 판단한다.
- Runner는 **outbound 연결만** 사용(큐 폴링, MinIO 업로드)하므로 해석 서버에 inbound 포트를 열 필요가 없다.
- Abaqus 라이선스 토큰 관리: Runner가 실행 전 토큰 가용량을 확인(`abaqus licensing` 또는 lmstat 파싱)하고, 부족 시 작업을 큐에 유지한다.

## 4. Runner(Tool Adapter) 상세

Runner는 DTOS에서 가장 실패하기 쉬운 지점(외부 도구 실행)을 격리하는 컴포넌트다.

```
[작업 수신]  Redis 큐에서 ToolJob 수신
    → workdir 생성, MinIO에서 입력 아티팩트 다운로드
[사전 검사]  체크섬, 라이선스 토큰, 디스크 용량
[실행]      subprocess로 도구 실행 (abaqus job=... interactive)
    → stdout/stderr 스트리밍 → 로그 아티팩트 + 진행 이벤트 발행
[후처리]    상태 파일(.sta/.msg/.log) 파싱 → 수렴성/에러 1차 판정
    → 결과 파일(.odb 등) MinIO 업로드
[보고]      ToolJobResult(status, artifacts[], metrics{}) 발행
```

- Runner는 LLM을 호출하지 않는다. **결정적(deterministic) 실행기**로 유지해 장애 원인을 분리한다.
- 타임아웃, 재시도 횟수, 동시 실행 슬롯은 Runner 설정으로 관리한다.
- 동일 계약으로 `fmu-runner`, `doc-renderer`, (Phase 4) `isaacsim-runner`를 추가한다.

## 5. 데이터 저장 구조 (계획서 9장 구체화)

### 5.1 PostgreSQL 핵심 스키마 (요약)

```
projects(id, name, customer, domain, status, created_at, ...)
workflow_defs(id, key, version, yaml, input_schema, created_by, is_active)
runs(id, project_id, workflow_def_id, status, requested_by, task_plan_json,
     started_at, finished_at)                     -- 워크플로우 실행 1건
steps(id, run_id, agent, name, status, attempt, input_ref, output_ref,
      error_class, started_at, finished_at)       -- run-level ledger의 단위
approvals(id, step_id, gate_key, decision, reviewer, comment, decided_at)
artifacts(id, run_id, step_id, kind, uri, checksum, size, meta_json)
templates(id, kind{inp|script|report|vnv}, key, version, uri, param_schema,
          validated_by, validated_at)
materials(id, name, source, props_json, valid_range_json)
requirements(id, project_id, kind{UR|SR|SWR|TC}, code, text, parent_id)
trace_links(id, from_req, to_req|to_artifact, link_type)   -- Traceability
llm_calls(id, step_id, model, prompt_ref, completion_ref, tokens, cost, latency)
```

### 5.2 Artifact Store (MinIO) 경로 규약

```
s3://dtos/{project}/{run}/{step}/{filename}
  예) s3://dtos/PRJ-024/run-0113/cae-job/drop_v3.odb
      s3://dtos/PRJ-024/run-0113/report/final_ko.docx
```

- 모든 아티팩트는 불변(immutable). 수정은 새 버전 업로드 + `artifacts` 행 추가.
- 보고서에 삽입되는 그림/표도 아티팩트로 등록해 보고서↔결과 추적성을 확보한다.

### 5.3 지식 저장 (계획서 9장 매핑)

| 계획서 항목 | MVP 구현 | Phase 3 확장 |
|---|---|---|
| Project Memory | `projects` + 과거 run 요약을 pgvector에 임베딩 | 유사 프로젝트 추천 랭킹 |
| Simulation Template | `templates` 테이블 + MinIO(파일) + param_schema(JSON Schema) | 템플릿 자동 추천 |
| Material DB | `materials` (유효범위 포함 → Quality Gate가 범위 검사) | 외부 물성 DB 연동 |
| V&V Knowledge | CoU/QoI/MRA 템플릿 + Test Case 카탈로그 | Knowledge Graph 승격 |
| Prompt/Agent Log | `llm_calls` + `steps` | 프롬프트 회귀 평가셋 자동 구축 |

## 6. Evaluation Layer와 KPI 집계

### 6.1 Quality Gate (룰 엔진)

Gate는 워크플로우 정의에 선언적으로 붙는다(02 문서 참조). MVP 룰 예시:

| Gate | 검사 | 실패 시 |
|---|---|---|
| `gate.input.units` | 단위계 일관성(SI/mm-t-s), 물성 필수 필드 | Agent 재시도(파라미터 수정) |
| `gate.input.material_range` | 물성값이 Material DB 유효범위 내인지 | HITL 확인 요청 |
| `gate.run.convergence` | .sta 파싱: 수렴 실패 increment 비율 | 재해석 제안 or HITL |
| `gate.run.energy` | ALLAE/ALLIE 비율 < 임계값(기본 10%) | HITL |
| `gate.report.consistency` | 본문 수치 = 결과 테이블 수치 일치 | Report Agent 재생성 |

### 6.2 KPI 자동 집계 (계획서 12장의 측정 가능화)

| KPI | 산식 (ledger 기반) |
|---|---|
| 자동 실행률 | `steps.status=succeeded AND attempt=1` / 전체 steps (사람 개입 없이 1회에 성공) |
| Quality Gate Pass율 | gate 통과 step / gate 대상 step |
| 보고서 시간 단축 | run 시작→보고서 승인까지 경과시간 vs 수작업 기준선(초기 3건 실측) |
| 재사용성 | 동일 `workflow_def`/`template`을 사용한 프로젝트 수 |

### 6.3 Test Harness (Phase 2)

- 대표 시나리오(소형 메시 낙하해석 등)를 **소요 10분 이내의 축소판**으로 만들어 야간 회귀 실행
- 프롬프트/템플릿/모델 버전 변경 시 자동 회귀 → 성공률 대시보드

## 7. 보안 설계 요약

| 항목 | MVP | Phase 3+ |
|---|---|---|
| LLM 외부 전송 | LLM Gateway에서 고객명/제품명/식별 수치 마스킹(사전 등록 사전 기반 치환) | 온프레미스 vLLM 옵션(게이트웨이 라우팅 전환만으로 교체) |
| 인증 | 사내 SSO(OIDC) 또는 로컬 계정 | 프로젝트별 RBAC |
| 감사 추적 | `llm_calls`·`steps`·`approvals` 원장 | 감사 리포트 자동 생성 |
| 해석 서버 | inbound 차단, Runner outbound only | 네트워크 분리 존 |
