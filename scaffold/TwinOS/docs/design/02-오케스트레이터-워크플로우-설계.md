# AI Orchestrator 및 Agent 간 Workflow / 데이터 흐름 설계

> 계획서 5.1(AI Orchestrator)의 구현 설계. LangGraph 기반.
>
> **주**: 본 문서의 `drop_test` 예시는 설계 설명용으로 유지한다. MVP 확정 워크플로우는 **`fmh_impact/1.0`** 이며 [08 문서 §5](08-FMH-DigitalTwin-Plugin-설계.md)에 정의되어 있다. Orchestrator의 동작 원리(Task Plan, HITL, 실패 복구, foreach 팬아웃)는 두 워크플로우에 동일하게 적용된다.

---

## 1. Orchestrator의 책임 범위 (하는 것 / 하지 않는 것)

| 하는 것 | 하지 않는 것 |
|---|---|
| 자연어 요청 → Task Plan JSON 변환 | 도구 직접 실행 (Runner의 일) |
| 워크플로우 카탈로그에서 매칭 + 파라미터 바인딩 | 워크플로우 YAML 동적 생성 (Phase 3 과제) |
| Agent 호출 순서 제어, 병렬 분기, 재시도 | Agent 내부 로직 개입 |
| HITL 게이트에서 일시정지/재개 (checkpoint) | 사람 승인 없는 Quality Gate 우회 |
| 실패 분류 및 대안 경로 선택 | LLM 산출물의 무검증 실행 |

## 2. 요청 처리 파이프라인

```
사용자: "PRJ-024 낙하충돌 해석 조건 만들어서 돌리고 보고서까지 만들어줘.
        높이 1.2m, 바닥 콘크리트, 제품은 지난번 v3 모델."

[1] Intent 해석 (LLM + RAG)
    · 프로젝트 컨텍스트 로드(PRJ-024 과거 run, 모델 v3 아티팩트)
    · Task Plan JSON 생성 (아래 3장)
[2] 워크플로우 매칭
    · 카탈로그에서 workflow=drop_test_v1 선택 (LLM 분류 + confidence)
    · confidence < 임계값 → 사용자에게 후보 제시(모호성 해소 질문)
[3] 파라미터 바인딩 + 사전 검증
    · drop_height=1.2m, floor=concrete, model=artifact://PRJ-024/model-v3
    · gate.input.* 룰 통과 확인, 누락 파라미터는 사용자에게 질문
[4] 실행 계획 승인 (HITL Gate #1 — MVP 필수)
    · "이 계획으로 실행합니다" 요약 + 예상 소요시간/라이선스 사용 → 승인
[5] 실행 (LangGraph 그래프 실행, 각 노드 = Agent Task)
[6] 결과 승인 (HITL Gate #2) → 보고서 발행
```

## 3. Task Plan JSON (표준 스키마)

```json
{
  "plan_id": "plan-8f21",
  "project_id": "PRJ-024",
  "intent": "drop_impact_analysis",
  "workflow": {"key": "drop_test", "version": "1.3"},
  "inputs": {
    "model_ref": "artifact://PRJ-024/model-v3/assembly.inp",
    "drop_height_m": 1.2,
    "floor_material": "concrete",
    "orientations": ["face_down", "corner_3"],
    "mesh_refinement": "default"
  },
  "deliverables": [
    {"kind": "report", "format": "docx", "template": "customer_std_v2"},
    {"kind": "summary", "format": "html"}
  ],
  "verification": ["gate.run.convergence", "gate.run.energy", "gate.report.consistency"],
  "constraints": {"deadline": null, "max_license_tokens": 5},
  "open_questions": []
}
```

- `open_questions`가 비어 있지 않으면 Orchestrator는 실행 전 사용자에게 질문한다.
- Task Plan은 `runs.task_plan_json`에 저장되어 감사 추적의 시작점이 된다.

## 4. Workflow 정의 (카탈로그 항목)

워크플로우는 사람이 작성·버전관리(Git)하는 YAML이다. Orchestrator는 이를 LangGraph 그래프로 로드한다.

```yaml
# workflows/drop_test/1.3.yaml
key: drop_test
version: "1.3"
description: 낙하충돌 해석 → 검증 → 보고서
input_schema: schemas/drop_test_input.json      # JSON Schema로 바인딩 검증

steps:
  - id: prepare_case
    agent: cae
    action: generate_case          # 템플릿 선택 + 파라미터 주입
    gates_after: [gate.input.units, gate.input.material_range]

  - id: approve_plan
    type: hitl                     # 사람 승인 게이트
    gate_key: plan_approval
    show: [prepare_case.output.case_summary]

  - id: run_jobs
    agent: cae
    action: run_job
    foreach: inputs.orientations   # 방향별 병렬 실행 (라이선스 슬롯 내)
    retry: {max: 2, on: [tool_transient_error]}
    gates_after: [gate.run.convergence, gate.run.energy]
    on_gate_fail: escalate_hitl    # 수렴 실패 → 사람 판단

  - id: extract_results
    agent: cae
    action: extract_results        # ODB → 지표/그래프/이미지 아티팩트

  - id: verify
    agent: vnv
    action: check_results          # 기준값 초과 여부, 판정표 생성

  - id: draft_report
    agent: report
    action: generate
    inputs:
      results: extract_results.output
      verdicts: verify.output
    gates_after: [gate.report.consistency]

  - id: approve_report
    type: hitl
    gate_key: report_approval
    on_reject: draft_report        # 반려 사유를 입력으로 재생성 루프
```

핵심 규칙:

- **step의 입출력은 전부 아티팩트 참조 + 소형 JSON**. 대용량 파일은 절대 그래프 상태에 넣지 않는다.
- `type: hitl` 노드에서 LangGraph checkpoint(Postgres)로 상태를 저장하고 그래프를 **중단**한다. 승인 API 호출 시 해당 checkpoint에서 재개한다. 며칠 뒤 승인해도 재개 가능해야 한다 (해석 Job이 몇 시간~며칠 걸리는 도메인 특성상 필수).
- `foreach`는 Celery 병렬 팬아웃으로 구현하고, 그래프는 전체 완료를 join한다.

## 5. 실패 복구 설계 (계획서 5.1 "실패 복구" 구체화)

실패를 4종으로 분류하고 대응을 자동화한다. 분류는 Runner/Agent가 `error_class`로 보고한다.

| error_class | 예 | 자동 대응 |
|---|---|---|
| `tool_transient_error` | 라이선스 일시 부족, 네트워크, 디스크 | 백오프 재시도 (max 2) |
| `tool_numerical_error` | 수렴 실패, excessive distortion | 사전 정의 대안(예: mass scaling 조정, 초기 increment 축소) 1회 시도 → 실패 시 HITL |
| `agent_generation_error` | 파라미터 추출 실패, 스키마 불일치 | 프롬프트 재시도(온도↓, 오류 피드백 주입) max 2 → HITL |
| `input_error` | 물성 누락, 모델 파일 손상 | 즉시 사용자 질문 (재시도 무의미) |

- 모든 재시도는 `steps.attempt`로 원장에 남는다 → "자동 실행률" KPI의 분모/분자.
- **대안 Tool 선택**(계획서 표현)은 MVP에서 제외한다. 대안 경로는 워크플로우 YAML에 명시된 것만 허용(예: `on_gate_fail`). 임의의 도구 전환은 검증 불가.

## 6. Agent 간 데이터 흐름 (MVP Use Case 1 전체)

```
 사용자          Orchestrator        CAE Agent        Abaqus Runner       V&V Agent    Report Agent
   │ 요청           │                    │                  │                 │             │
   ├───────────────▶│ TaskPlan 생성       │                  │                 │             │
   │◀── 계획 승인요청 ┤ (HITL#1)           │                  │                 │             │
   ├ 승인 ─────────▶│                    │                  │                 │             │
   │                ├─ generate_case ───▶│ 템플릿+파라미터     │                 │             │
   │                │◀─ case.inp, summary┤ → artifacts       │                 │             │
   │                ├─ run_job ─────────▶│─ ToolJob(큐) ────▶│ abaqus 실행      │             │
   │                │   (foreach 방향)    │                  │ .sta 진행 이벤트─▶ WebSocket → UI
   │                │◀─ odb, logs, metrics ────────────────── ┤                 │             │
   │                ├─ gate.run.* 판정    │                  │                 │             │
   │                ├─ extract_results ─▶│ ODB→지표/이미지    │                 │             │
   │                ├─ check_results ────────────────────────────────────────▶│             │
   │                │◀─ 판정표(pass/fail, 근거) ──────────────────────────────── ┤             │
   │                ├─ generate ────────────────────────────────────────────────────────────▶│
   │                │◀─ report.docx, summary.html ───────────────────────────────────────────┤
   │◀── 보고서 승인요청┤ (HITL#2)          │                  │                 │             │
   ├ 승인/반려 ─────▶│ (반려 시 사유와 함께 draft_report 재실행)                                  │
```

데이터 계약 요점:

- CAE Agent → V&V Agent: `results.json` (QoI별 최대값/위치/시계열 아티팩트 참조)
- V&V Agent → Report Agent: `verdicts.json` (기준, 측정값, 판정, 근거 문장)
- Report Agent는 **수치를 재계산하지 않는다** — 전달받은 JSON만 렌더링 (일관성 게이트로 검증)

## 7. Orchestrator 자체 API (내부)

| Method | Path | 설명 |
|---|---|---|
| POST | `/runs` | Task Plan 제출 → run 생성 (자연어 요청은 `/intents`가 선처리) |
| POST | `/intents` | 자연어 → Task Plan JSON (미확정 질문 포함 반환) |
| GET | `/runs/{id}` | run 상태 + step 트리 |
| POST | `/runs/{id}/approvals/{gate_key}` | HITL 승인/반려 (checkpoint 재개) |
| POST | `/runs/{id}/cancel` | 실행 취소 (Runner에 취소 신호 전파) |
| GET | `/runs/{id}/events` (WS) | 진행 이벤트 스트림 |
| GET | `/workflows` | 카탈로그 목록/버전 |

## 8. 단계별 지능 확장 로드맵

| 단계 | Orchestrator 지능 수준 |
|---|---|
| MVP | 워크플로우 분류 + 파라미터 추출 + 질문 생성 (LLM 사용은 이 3곳뿐) |
| Phase 2 | 실패 로그 요약·원인 추정, 재해석 파라미터 제안 (사람 승인 후 적용) |
| Phase 3 | 기존 step 블록을 조합한 워크플로우 **초안** 합성 (사람이 카탈로그에 등록해야 실행 가능) |
| Phase 4 | 크로스 도메인 계획 (CAE+FMU+Sim 복합 시나리오) |
