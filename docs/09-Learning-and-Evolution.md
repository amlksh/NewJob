# DTOS Learning & Evolution (학습·진화 체계)

> DTOS(AI 기반 Digital Twin Operating System)가 **운영할수록 좋아지는 플랫폼**이 되기 위한 학습 루프 설계.
> 전제(계획서 15장·00 문서): DTOS의 학습은 **LLM 재학습이 아니라, 검증된 자산·지식·평가 데이터의 축적과 승격**으로 이루어진다. 모델 파인튜닝은 마지막 수단이다.

---

## 1. 학습의 원천: 운영 데이터는 이미 설계되어 있다

01~08 문서의 설계가 그대로 학습 데이터 파이프라인이 된다. 새 수집 체계를 만드는 것이 아니라, **이미 원장에 쌓이는 것을 학습 신호로 재해석**한다.

| 운영 데이터 (원천 설계) | 학습 신호로서의 의미 |
|---|---|
| `steps` ledger (성공/실패/attempt/error_class) | 어떤 작업이 자동화에 강하고 약한지, 재시도 패턴 |
| `approvals` (승인/반려 + 사유 코멘트) | **사람 전문가의 판단 라벨** — 가장 값진 데이터 |
| `llm_calls` (프롬프트/응답/모델/비용) | 프롬프트 회귀 평가셋의 원료 |
| Quality Gate 판정 이력 | 게이트 임계값의 적정성, 오탐/미탐 |
| `artifacts` + lineage (URN 계보) | 해석 입력→결과 쌍 = 대리모델(surrogate) 학습 데이터셋 |
| Report `revise` 이력 (반려 사유→수정 diff) | 보고서 품질 개선 신호 |
| HITL 질문·응답 (`open_questions`) | Intent 해석이 놓치는 정보 유형 |

**MVP에서 해야 할 일은 이 데이터를 "버리지 않는 것"뿐이다.** 학습 루프 자체는 Phase 2부터 가동한다.

## 2. 4개의 학습 루프

```
                ┌──────────────────────────────────────────────┐
                │              DTOS 운영 (runs)               │
                └───┬──────────┬───────────┬───────────┬───────┘
                    │          │           │           │
      ┌─────────────▼──┐ ┌─────▼─────┐ ┌───▼────────┐ ┌▼──────────────┐
      │ Loop A         │ │ Loop B    │ │ Loop C     │ │ Loop D        │
      │ Knowledge      │ │ Template/ │ │ Prompt &   │ │ Surrogate/ML  │
      │ (지식 축적)      │ │ Workflow  │ │ Model      │ │ (H2~H3)       │
      │                │ │ (자산 진화) │ │ (LLM 개선)  │ │               │
      └─────────────┬──┘ └─────┬─────┘ └───┬────────┘ └┬──────────────┘
                    │          │           │           │
                    └──────────┴─────┬─────┴───────────┘
                                     ▼
                        승격 게이트 (사람 승인 + 회귀 통과)
                                     ▼
                        Registry/카탈로그 반영 → 다음 run이 더 잘함
```

**공통 규칙 — 승격(Promotion) 게이트**: 어떤 루프의 산출물도 자동으로 운영에 반영되지 않는다. `초안 생성(자동) → Test Harness 회귀 통과 → 사람 승인 → 버전 승격` 절차를 강제한다. 이는 00 문서 2.1(자유 생성 금지)과 같은 철학의 학습 버전이다.

### Loop A — Knowledge Loop (지식 축적) · Phase 2 가동

run이 끝날 때마다 지식이 자동 적재되고, 다음 Intent 해석·계획 수립이 좋아지는 루프.

| 단계 | 내용 |
|---|---|
| 수집 | run 완료 시 자동 요약 생성: 목적, 입력 조건, 결과 요지, 실패·재시도 이력, 승인 코멘트 |
| 적재 | 요약을 pgvector에 임베딩 (`run_summaries`), 원문은 아티팩트 참조 |
| 활용 | ① Intent 해석 시 유사 run 검색 → 파라미터 제안·주의사항 주입 ② "이 조건이면 지난번 PRJ-031에서 수렴 문제가 있었음" 류의 사전 경고 |
| 승격 | 반복 확인된 패턴은 사람이 **Playbook**(도메인 절차 지식)으로 정리해 Plugin의 지식 파일로 승격 → RAG 검색 결과보다 우선 적용 |

### Loop B — Template/Workflow Evolution (자산 진화) · Phase 2 가동

반려·게이트 실패 통계가 템플릿과 워크플로우의 개정으로 이어지는 루프. **DTOS의 경쟁력 자산(검증된 템플릿)이 성장하는 메커니즘이다.**

| 단계 | 내용 |
|---|---|
| 감지 | 분기별(초기엔 월별) 자동 리포트: 템플릿별 게이트 실패율·반려 사유 클러스터링(LLM), 파라미터 분포 vs 유효범위 |
| 제안 | "템플릿 X의 접촉 정의가 반려 사유의 40%" → 개정 초안(LLM 생성) + 근거 run 목록 |
| 검증 | 개정 템플릿을 Test Harness 축소판 시나리오 + 과거 run 재현으로 회귀 검증 |
| 승격 | 도메인 전문가 승인 → `templates` 새 버전 등록, 구버전 deprecated. lineage로 어떤 run이 어떤 버전을 썼는지 항상 추적 가능 |

워크플로우도 동일 절차를 따른다(예: HITL 게이트 위치 조정, 재시도 정책 변경). Phase 3의 "워크플로우 초안 합성"(02 문서 8장)은 이 루프의 데이터가 충분히 쌓인 뒤에만 안전하다.

### Loop C — Prompt & Model Evolution (LLM 운영 개선) · Phase 2 가동

LLM 구성요소(Intent 해석, 파라미터 추출, 서술 생성)의 품질을 회귀 가능하게 만드는 루프.

| 단계 | 내용 |
|---|---|
| 평가셋 구축 | `llm_calls` + 사람의 최종 확정본(승인된 Task Plan, 수정된 보고서)에서 골든 평가셋 자동 후보 추출 → 사람 검수 후 등록. 목표: MVP 말 50문항, P2 말 200문항 |
| 회귀 | 프롬프트/모델/온도 변경 시 평가셋 자동 실행 → 정확도·비용·지연 비교 리포트. **회귀 없이 프롬프트 변경 금지** (Git으로 프롬프트 버전관리) |
| 모델 업그레이드 | 신규 모델 출시 시 평가셋으로 A/B → LLM Gateway 라우팅 전환. 온프레미스 전환 판단(00 문서 2.7)도 같은 평가셋으로 |
| 파인튜닝 (최후) | 평가셋으로 입증된 반복 실패 유형이 프롬프트로 해결 안 될 때만 검토 (H2 이후, 소형 모델의 구조화 추출 태스크 한정) |

### Loop D — Surrogate/ML Loop (대리모델) · H2~H3 가동

lineage가 완비된 해석 입출력 쌍이 대리모델 학습 데이터가 되는 루프 (07 문서 §8-H3의 실행 설계).

| 단계 | 내용 |
|---|---|
| 데이터셋 | Asset Registry에서 조건 충족 run 자동 추출: 동일 템플릿 계열 + validated 헤드폼/메시 + 게이트 통과. 예: FMH → (타겟 위치, 접근각, 트림 강성 파라미터) → HIC(d) |
| 학습 | 회귀 모델/GP/NN — 도메인별 선택. 학습 코드도 Plugin에 귀속(`plugins/fmh_twin/ml/`) |
| 등록 | `ml.surrogate` 자산으로 등록: 학습 데이터 lineage, 적용 범위(valid_scope), 오차 지표 필수 |
| 활용 | Simulation Graph fidelity_policy(07 문서 §4)로 스크리닝에 투입 — **대리모델 결과는 절대 최종 판정에 직접 사용 금지**, 워스트 후보 선별용. 최종 판정은 항상 고충실 해석 |
| 갱신 | 신규 run 축적 시 재학습 + 예측오차 모니터링(드리프트 감지) |

## 3. Agent/Plugin의 진화: Evaluation-driven

Agent Registry(07 문서 §3)의 `success_rate_30d`가 진화의 트리거다.

| 신호 | 대응 |
|---|---|
| 플러그인 회귀 스위트 성공률 하락 | 자동 알림 → 최근 변경(템플릿/프롬프트/모델/도구 버전) diff와 함께 원인 후보 리포트 |
| 특정 error_class 증가 | Loop B/C로 라우팅 (템플릿 문제 vs 프롬프트 문제 분류) |
| HITL 개입률 증가 | "자동화가 후퇴하는 지점" 리포트 — KPI(자동 실행률)와 연동 |
| 신규 도구 버전 (Abaqus 등) | Connector 버전 매트릭스로 회귀 후 승격 (운영 중 무단 업그레이드 금지) |

trust tier 승격/강등도 이 데이터로 결정한다: experimental → partner → core 승격 조건 = 회귀 스위트 + 운영 30일 성공률 + 도메인 전문가 리뷰.

## 4. 조직 학습: 사람-AI 협업의 진화

계획서 2장 ③(조직 최소화)의 실현은 자동화율이 아니라 **신뢰의 축적 속도**에 달려 있다.

1. **승인 위임의 단계화**: 초기엔 모든 게이트를 사람이 승인 → 특정 게이트의 판정 일치율이 N주 연속 목표치를 넘으면 **해당 게이트만 자동 통과로 전환**(사후 샘플링 검토로 대체). 전환·회수 이력은 원장에 기록. "무엇을 언제부터 AI에 맡겼는가"가 감사 가능해야 규제 산업에서 방어된다.
2. **반려 사유의 구조화**: 반려 시 자유 텍스트 + 사유 코드(조건 오류/물성/보고서 표현/판단 보류…)를 함께 입력받는다 — Loop B/C의 분류 품질이 여기서 결정된다. UI 설계(04 문서)에 반영.
3. **전문가 지식의 이관**: 시니어 엔지니어의 검토 기준을 Playbook·게이트 룰로 명문화하는 정기 세션(분기 1회). DTOS는 이것을 "지식이 사람에게만 있는 상태 → 플랫폼에 있는 상태"로 옮기는 조직적 장치로 사용한다.

## 5. 단계별 가동 로드맵

| Phase | 가동 항목 | 성과 판정 |
|---|---|---|
| **MVP (P1)** | 데이터만 완비: 원장·approvals 사유 코드·lineage·llm_calls. 학습 루프는 미가동 | 소급 분석 가능성 (P2 시작 시 MVP 데이터로 첫 리포트 생성) |
| **P2** | Loop A(지식), Loop B(템플릿 진화 — 월별), Loop C(평가셋 200문항 + 회귀 체계), Evaluation 대시보드 | 프롬프트 변경의 100%가 회귀 통과 후 배포. 템플릿 개정 ≥ 2건 승격 |
| **P3** | 승인 위임 단계화 시작, Playbook 체계, 워크플로우 초안 합성(Loop B 데이터 기반), 드리프트 모니터링 | 자동 통과 게이트 ≥ 1개 (판정 일치율 근거 포함), HITL 개입률 감소 추세 |
| **H2~H3 (P4+)** | Loop D(대리모델), sim-to-real 데이터 유입(06 문서), 파인튜닝 검토 | `ml.surrogate` 자산 등록 ≥ 1건 + 스크리닝 실적 |

## 6. 하지 않는 것 (Anti-goals)

1. **온라인 자동 학습 금지** — 운영 결과가 사람 승인 없이 프롬프트/템플릿/모델에 반영되는 경로를 만들지 않는다. 모든 개선은 승격 게이트를 지난다.
2. **MVP에서 학습 루프 구현 금지** — MVP는 데이터 스키마(사유 코드, lineage)까지만. 루프 구현을 앞당기면 03개월 일정이 깨진다.
3. **LLM 파인튜닝 선행 금지** — 프롬프트+RAG+템플릿으로 해결되지 않음이 평가셋으로 입증되기 전에는 착수하지 않는다.
4. **대리모델의 판정 사용 금지** — 스크리닝 전용. 규격 판정(HIC 등)은 항상 고충실 해석 + 사람 승인.
