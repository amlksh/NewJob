## 1. 총평

계획서의 방향성은 타당하다. 특히 아래 세 가지 판단은 성공 가능성을 높이는 올바른 결정이다.

1. **AI 모델을 새로 만들지 않고, 기존 CAE/FMU/V&V 업무를 오케스트레이션한다** — LLM은 상용 API/오픈 모델을 사용하고, 차별화 가치는 도메인 워크플로우·검증 룰·템플릿 자산에 둔다.
2. **사람은 검토·승인, AI는 실무 수행** — Human-in-the-loop(HITL)을 아키텍처의 1급 요소로 설계하면 규제 산업(의료기기)에서도 방어 가능한 구조가 된다.
3. **MVP → PoC → 플랫폼 → Physical AI 순의 단계화** — 범위 폭주를 막는 올바른 순서다.

다만 **"계획서 수준"에서 "구현 가능한 설계"로 넘어가려면 아래 7가지를 반드시 조정해야 한다.** 본 문서 세트는 이 조정을 반영한 설계안이다.

## 2. 현실성 보완이 필요한 항목과 대안

### 2.1 LLM의 자유 생성(free-form) 의존 → 템플릿 기반 파라미터화로 전환 (가장 중요)

- **문제점**: 계획서는 "해석 조건 자동 생성", "INP 수정안 생성", "Workflow YAML 자동 구성"을 LLM이 직접 생성하는 것으로 기술한다. LLM이 INP 파일이나 Abaqus 스크립트를 자유 생성하면 *그럴듯하지만 틀린* 결과(계획서 13장에서 스스로 지적한 리스크)가 MVP 단계부터 신뢰를 무너뜨린다.
- **대안**: **검증된 템플릿 + LLM 파라미터 추출** 구조로 전환한다.
  - 해석 시나리오별(낙하, FMH, 정적강도 등) INP/스크립트 템플릿을 사람이 사전 검증하여 Template DB에 등록
  - LLM의 역할은 ①사용자 요청에서 파라미터 추출(재료, 하중, 경계조건, 메시 밀도 등) ②템플릿 선택 ③파라미터 유효 범위 검증 요청으로 한정
  - 자유 생성은 Phase 3 이후, Evaluation Harness의 회귀 테스트가 갖춰진 뒤에 점진 허용
- **효과**: MVP 성공률이 "LLM 코드 생성 성공률"이 아니라 "템플릿 커버리지"로 결정되므로 예측 가능하고, 실패 시 원인 추적이 쉽다.

### 2.2 Workflow "자동 생성" → "사전 정의 워크플로우 선택 + 파라미터 바인딩"

- **문제점**: Orchestrator가 임의 요청에서 Workflow YAML을 동적으로 생성하는 것은 현재 기술로도 안정화에 수개월 이상 걸리는 고난도 과제다.
- **대안**: MVP에서는 **사전 정의된 워크플로우 카탈로그**(예: `drop_test_v1`, `fmu_cohort_validation_v1`)를 두고, Orchestrator는 (a) 요청 → 워크플로우 매칭, (b) 파라미터 바인딩, (c) 실행/모니터링/HITL 게이트 관리만 담당한다. 동적 워크플로우 합성은 Phase 3 과제로 명시한다.

### 2.3 MVP 3개월 범위 과다 → Use Case 1개로 축소

- **문제점**: 계획서 8장은 MVP에 Abaqus 낙하해석 자동화 + 질환 Solver cohort 검증 두 개를 모두 포함한다. 3~4명 인력으로 3개월 내 Web UI + Orchestrator + 2개 도메인 파이프라인 + 자동 검증은 현실적으로 불가능하다.
- **대안**: **MVP는 Use Case 1(Abaqus 낙하/FMH 해석 → 검증 → 보고서) 단일 파이프라인의 end-to-end 완주**로 정의한다. 질환 Solver/FMU는 Phase 2 첫 과제로 이동한다. 단, Agent API 계약(03 문서)을 처음부터 표준화해 Phase 2에서 FMU Agent가 "같은 계약을 구현하는 새 서비스"로 꽂히도록 한다.

### 2.4 Abaqus 실행 환경의 물리적 제약 명시 필요

- **문제점**: Abaqus는 라이선스 서버, 특정 OS(주로 Linux HPC 또는 Windows 워크스테이션), 토큰 기반 동시 실행 제약이 있다. 웹 백엔드 컨테이너에서 직접 실행할 수 없다.
- **대안**: **Tool Adapter(Runner) 데몬**을 해석 서버에 상주시키고, 백엔드와는 작업 큐(Celery/Redis) + 파일 스토리지(MinIO/공유 디스크)로만 통신하는 구조로 설계했다(01 문서 4장). 계획서 13장의 "초기에는 파일 기반 연동"과 같은 방향이며, 이를 아키텍처에 정식 반영했다.

### 2.5 CATIA Magic(Cameo) 연동 난이도

- **문제점**: CATIA Magic의 API(OpenAPI/Teamwork Cloud REST)는 버전 의존성이 크고 자동화 제약이 많다.
- **대안**: MBSE Agent는 **ReqIF/CSV 파일 교환을 표준 인터페이스**로 삼고, CATIA Magic 직접 연동은 "Import/Export 가능한 파일 생성"까지만 보장한다(Phase 3). Traceability Matrix는 DTOS 내부 DB에서 관리하고 필요 시 내보낸다.

### 2.6 KPI 측정 방법 정의 누락

- **문제점**: "자동 실행률 70%", "Pass율 90%"는 분모·분자 정의가 없으면 측정 불가.
- **대안**: Evaluation Layer에 **run-level 원장(ledger)** 을 두어 모든 Agent 실행을 `succeeded / failed / human_override` 로 기록하고, KPI를 여기서 자동 집계한다(01 문서 6장). MVP부터 로그 스키마에 포함해야 나중에 소급 측정이 가능하다.

### 2.7 보안/LLM 선택

- **문제점**: 온프레미스 LLM(vLLM)은 상용 API 대비 품질 격차가 있어, 처음부터 온프레미스로 가면 MVP 품질이 나오지 않을 수 있다.
- **대안**: MVP는 상용 API(Claude/OpenAI) + **민감정보 마스킹 게이트웨이**(고객명·프로젝트명·수치 치환)로 시작하고, LLM 호출을 단일 게이트웨이 모듈로 추상화해 Phase 3에서 온프레미스 전환 비용을 최소화한다.

## 3. 계획서 대비 설계안의 주요 변경 요약

| 항목 | 계획서 | 본 설계안 | 사유 |
|---|---|---|---|
| 해석 조건 생성 | LLM 자유 생성 | 검증된 템플릿 + 파라미터 추출 | 신뢰성, 원인 추적 |
| Workflow | LLM이 YAML 동적 생성 | 사전 정의 카탈로그 + 바인딩 | 안정화 기간 단축 |
| MVP Use Case | 2개(Abaqus + 질환 Solver) | 1개(Abaqus) — FMU는 Phase 2 | 인력/기간 현실성 |
| Frontend | React 또는 Streamlit | MVP: 경량 React(SPA 1장) 권장, 초기 2주는 Streamlit 허용 | 승인 UX는 Streamlit로 한계 |
| Workflow 엔진 | Celery/Airflow/Prefect 중 미정 | MVP: Celery+Redis, Phase 3: Prefect 승격 검토 | 장시간 Job + 단순성 |
| Agent Framework | LangGraph/AutoGen/CrewAI 중 미정 | LangGraph 확정 (checkpoint/HITL 내장) | 승인 게이트·재개 필수 |
| MBSE 연동 | CATIA Magic 연계 | ReqIF/CSV 파일 표준, Magic은 Import/Export | API 제약 |
| KPI | 목표치만 정의 | run-level 원장 기반 자동 집계 설계 포함 | 측정 가능성 |
